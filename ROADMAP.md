## Требования и границы первой версии

Обязательные требования задания:

- Сервер отдаёт поездки и финансовую сводку за выбранный день.
- Клиент показывает сводку и список поездок и позволяет переключать дни.
- Через API можно добавить поездку с проверкой данных.
- Повторная отправка той же поездки не создаёт дубль.
- Расчёты сводки и защита от дублей покрыты тестами.
- Для сдачи нужен публичный репозиторий с README о запуске и выполненной работе,
  а также честное описание применения ИИ. Демо и скриншоты необязательны.

Дополнительно включены простая форма добавления во Flutter, аккуратный интерфейс,
CI и скриншоты. Целевые платформы — Android и iOS.

Первая версия рассчитана на одного водителя. Авторизация, несколько водителей,
офлайн-синхронизация и публичный деплой в неё не входят.
Публикация репозитория и отправка анкеты выполняются отдельно по запросу пользователя.

## Правила данных и расчётов

- Валюта — KZT. `amount` и `commission` — целые тенге. Использовать целочисленные
  поля в API, БД и Dart; не применять `float`/`double` для денег.
- `commission` — денежная сумма, а не процент. Она должна быть неотрицательной.
- Выручка — сумма `amount`; комиссия — сумма `commission`;
  «на руки» — выручка минус комиссия.
- Наличные и карта — суммы выручки по соответствующему способу оплаты.
  Их сумма равна общей выручке.
- Число поездок — количество записей за выбранный день.
- День определяется началом поездки в часовом поясе `Asia/Almaty`, независимо
  от часового пояса телефона или процесса сервера.
- Поездка через полночь целиком относится к дню начала.
- Интервал дня включает местную полночь и исключает полночь следующего дня.
- В API `start` и `end` передаются в ISO 8601 с часовым смещением.
  При хранении и сравнении нормализовать время в UTC.
- Пустой день возвращает пустой список и нулевые показатели.

## Минимальный контракт API

### Чтение дня

`GET /api/v1/days/{date}`, где `date` имеет формат `YYYY-MM-DD`.

Ответ содержит выбранную дату, список поездок и сводку: число поездок, выручку,
комиссию, «на руки», выручку наличными и картой. Денежные значения — целые числа.
Поездки отсортированы по времени начала, новые сверху.

### Добавление поездки

`POST /api/v1/trips` принимает поля исходного формата:

| Поле | Значение |
|---|---|
| `id` | Строковый идентификатор поездки |
| `start` | Начало, ISO 8601 с часовым смещением |
| `end` | Окончание, ISO 8601 с часовым смещением |
| `amount` | Положительное целое число тенге |
| `payment` | `cash` или `card` |
| `commission` | Неотрицательное целое число тенге |

Окончание должно быть строго позже начала. Неверные данные возвращают `422`.

| Сценарий | Результат |
|---|---|
| Новый ID и корректные данные | `201`, созданная поездка |
| Тот же ID и те же нормализованные данные | `200`, существующая поездка |
| Тот же ID и другие данные | `409`, конфликт |

Уникальность ID обеспечивает БД. Защита должна работать при конкурентных запросах
и после перезапуска сервера, без реестра ID только в памяти.
Равные моменты времени с разными часовыми смещениями считаются равными.
Разные ID обозначают разные поездки, даже если остальные поля совпали.

Flutter генерирует UUID один раз на отправляемую поездку.
При повторе после сетевой ошибки сохраняются и ID, и данные запроса.
Импорт JSON использует те же правила идентичности и конфликта.

### Этап 2. Данные и расчёты

**Зависимости:** этап 1.

**Задачи:**

- Добавить модель поездки, начальную миграцию и уникальность ID в БД.
- Реализовать чтение поездок за день и расчёт сводки независимо от HTTP.
- Добавить исходный JSON из задания и команду его импорта в SQLite.
- Реализовать повторяемый импорт с нормализацией времени и обработкой конфликтов ID.
- Написать тесты расчётов, границ дня и повторного импорта.

**Результат:** поездки хранятся в SQLite, импортируются и участвуют в корректной сводке.

**Проверки и готовность:** миграция работает на чистой БД; контрольный пример совпадает
с ожидаемым; пустой день, разные смещения и переход через полночь проверены;
повтор импорта не увеличивает число поездок; данные сохраняются после перезапуска.

**Реализация и команды этапа 2:**

- `backend/app/db/models.py`: таблица `trips`, строковый первичный ключ `id`,
  индекс начала поездки, обязательные поля и ограничения суммы, комиссии,
  способа оплаты и порядка времени. Денежные поля — SQLite `INTEGER`;
  дробные значения не могут храниться как деньги.
- Миграция `0001_create_trips` создаёт таблицу и индекс; Alembic подключён
  к metadata модели. Создание таблиц выполняется миграцией, а не при запуске приложения.
- `TripData` проверяет данные независимо от HTTP: целые суммы без преобразования
  строк, дробных чисел и bool, допустимую оплату и время с часовым смещением.
  Начало и окончание нормализуются в UTC. `UTCDateTime` сохраняет UTC в SQLite
  и восстанавливает часовое смещение при чтении.
- `save_trip` использует ограничение первичного ключа и SQLite
  `ON CONFLICT (id) DO NOTHING`. Сравниваются все нормализованные поля:
  тот же ID и данные дают повтор, изменённые данные — `TripConflictError`,
  разные ID создают отдельные поездки. Транзакцией управляет вызывающая сторона.
- `get_day` выбирает поездки по началу в полуоткрытом интервале дня
  `Asia/Almaty`, сортирует новые сверху и рассчитывает сводку целочисленно.
  Суммы сводки рассчитываются в Python и не ограничены диапазоном SQL `SUM`.
  Пустой день возвращает пустую коллекцию поездок и нулевые показатели.
- `backend/data/trips.json` содержит контрольный исходный пример из roadmap.
  Импорт сначала проверяет весь UTF-8 JSON-массив, затем записывает его одной
  транзакцией. Конфликт ID или ошибка записи откатывают весь импорт;
  команда сообщает количество созданных записей и повторов.
- Техническое ограничение хранения SQLite: каждое отдельное денежное значение
  должно помещаться в знаковый 64-битный `INTEGER` (максимум
  `9223372036854775807`). Превышение диапазона отменяет импорт с понятной ошибкой;
  преобразования денег в `float` нет.

Из `backend/`, после настройки uv из этапа 1:

```sh

uv run --locked alembic upgrade head
uv run --locked python -m app.import_trips data/trips.json
# Повтор этой команды сохраняет две поездки: создано 0, повторов 2.
```

`DATABASE_URL` задаёт ту же БД для миграции, импорта и сервера. По умолчанию
используется `backend/driver_diary.db`; рабочая БД остаётся вне Git.
Команда импорта требует предварительной миграции и не выполняет её автоматически.

### Этап 3. API и защита от дублей

**Зависимости:** этап 2.

**Задачи:**

- Реализовать два согласованных endpoint и схемы Pydantic.
- Подключить валидацию и операции БД к API, документировать ответы в OpenAPI.
- Обработать конкурентное создание одного ID с опорой на ограничение БД.
- Написать API-тесты чтения, добавления, валидации, повторов и конфликтов.

**Результат:** клиент может получить день и безопасно добавить поездку.

**Проверки и готовность:** соблюдаются статусы `201`, `200`, `409`, `422`;
одновременные повторы создают ровно одну запись и не удваивают сводку.
Для конкурентных проверок использовать отдельные сессии и временную файловую SQLite.

**Реализация и команды этапа 3:**

- `GET /api/v1/days/{date}` возвращает `date`, массив `trips` и объект `summary`.
  Поля сводки: `trip_count`, `revenue`, `commission`, `net_income`, `cash`, `card`.
  Все показатели — целые числа; `cash`/`card` содержат выручку, а `net_income`
  может быть отрицательным. Порядок поездок и границы дня берутся из логики этапа 2.
- `POST /api/v1/trips` принимает шесть согласованных полей и возвращает поездку
  в том же формате. Новый ID даёт `201`, повтор нормализованных данных — `200`,
  другие данные того же ID — `409` с объектом `{"detail": "…"}`.
  Некорректные данные — `422` со стандартным массивом ошибок FastAPI в `detail`.
  Время в обоих ответах сериализуется в UTC с суффиксом `Z`.
- HTTP-схемы используют общую валидацию `TripData`. Дополнительно на входе API
  денежные значения ограничены диапазоном SQLite INTEGER: максимум
  `9223372036854775807` для каждого поля. Превышение возвращает `422` до записи.
  Дата дня проверяется строго как `YYYY-MM-DD`; непредставимые границы дня в UTC
  также возвращают `422`. Суммы сводки по-прежнему могут превышать диапазон SQLite.
- На каждый HTTP-запрос создаётся отдельная SQLAlchemy-сессия. Engine и фабрика
  сессий создаются при запуске приложения из `DATABASE_URL`; engine освобождается
  при остановке. Миграции при запуске автоматически не выполняются.
- Сервис добавления использует существующий `save_trip` с первичным ключом и
  `ON CONFLICT (id) DO NOTHING`. Запись и сравнение данных выполняются в одной
  транзакции; commit завершается до ответа `201`/`200`. Конфликт и ошибка commit
  откатывают транзакцию. Реестра ID или блокировки только в памяти приложения нет.
- `/openapi.json` и `/docs` описывают схемы запросов/ответов, целочисленные деньги,
  UTC и результаты `201`, `200`, `409`, `422`. Точный максимум денег указан также
  в описаниях полей: FastAPI округляет числовой `maximum` в OpenAPI, но входная
  валидация Pydantic сравнивает целые числа точно.

Из `backend/`, после настройки uv и миграции из предыдущих этапов:

{"id":"t1","start":"2026-10-01T08:10:00+05:00","end":"2026-10-01T08:32:00+05:00","amount":2400,"payment":"card","commission":360}

### Этап 5. Добавление поездки

**Зависимости:** этап 4.

**Задачи:**

- Добавить простую форму: начало, окончание, сумма, способ оплаты и комиссия.
- Проверять ввод до отправки, показывать ошибки сервера и блокировать повторное
  нажатие во время активного запроса.
- Генерировать ID один раз и повторять тот же запрос при неопределённом результате
  из-за сетевой ошибки; не генерировать новый ID при повторе.
- После успеха обновить список и сводку затронутого дня.
- Написать тесты формы, состояния отправки и повторного использования ID.

**Результат:** сценарий добавления доступен с телефона.

**Проверки и готовность:** корректная поездка появляется в данных нужного дня;
ошибки понятны пользователю; двойное нажатие и повтор запроса не создают дубль.

**Реализация этапа 5:**

- С экрана дня открывается русская форма Material 3: отдельные даты и время
  начала/окончания, сумма, комиссия и наличные/карта. Ввод времени явно относится
  к `Asia/Almaty`; отдельная дата окончания позволяет поездку через полночь.
  Поля и ошибки находятся в прокручиваемой форме.
- `TripInput` проверяет порядок времени, представимость UTC и диапазон дня,
  положительную целую сумму и неотрицательную целую комиссию до максимума SQLite
  **9223372036854775807**. Деньги читаются и отправляются через `BigInt` без
  округления; комиссия может превышать сумму. Несуществующее историческое время
  Алматы отвергается; для повторяющегося времени выбирается одно определённое
  смещение библиотеки `timezone`.
- `TripApi` отправляет `POST /api/v1/trips`, принимает `201`/`200` и проверяет
  все поля подтверждения против отправленного запроса. Времена отправляются в UTC
  с `Z`, деньги — целыми JSON-числами. Ошибки `422` и `409` имеют понятные русские
  сообщения; таймаут, сеть, `5xx` и неверное подтверждение оставляют результат
  неизвестным и предлагают повтор той же поездки.
- `TripSubmission` создаёт UUID v4 через `Random.secure()` один раз и синхронно
  блокирует второй запрос. При неизвестном результате сохраняются ID и все поля;
  редактирование блокируется, а повтор отправляет исходный запрос. Закрытие
  и открытие формы, в том числе с другого дня, сохраняет ожидающую поездку.
  После `422` можно исправить данные с прежним ID; после `409` явное возвращение
  к форме начинает новую отправку. Во время запроса закрытие формы блокируется.
- После подтверждённого успеха сбрасывается ожидающая отправка и обновляется
  `dayProvider` дня начала поездки. Выбранная дата не меняется; сообщение об успехе
  указывает затронутый день, если он отличается от выбранного.
- Ожидающая поездка сохраняется в памяти текущего приложения. Восстановление

Ожидаемая сводка за 1 октября 2026 года:

Обязательные сценарии проверки:

- Пустой день, наличные и карта, нулевая комиссия, точность целочисленных сумм.
- Начало ровно в полночь, конец интервала дня, поездка через полночь,
  разные часовые смещения и независимость от системного часового пояса.
- Нулевая/отрицательная/дробная сумма, отрицательная/дробная комиссия,
  неверный способ оплаты, неверная дата и время без смещения,
  окончание раньше начала или одновременно с ним.
- Последовательные и конкурентные повторы, конфликт данных одного ID,
  повторный импорт и сохранность после перезапуска.
- Во Flutter: смена дней, запоздалые ответы, загрузка, ошибка и повтор,
  пустой день, форма, добавление и обновление сводки.
