# Инструкции для работы над проектом

Проект — тестовое задание arqa «Дневник смен водителя».
Источник требований и согласованных решений: [ROADMAP.md](ROADMAP.md).
Эти инструкции действуют для всего проекта. Явные указания пользователя имеют приоритет.

## Порядок работы

1. Перед изменениями прочитать roadmap, статус этапов и текущее состояние проекта.
2. Выполнять только этап или часть этапа, явно запрошенные пользователем.
   Не начинать следующий этап автоматически и не реализовывать всё тестовое за один раз.
3. Внутри запрошенного этапа самостоятельно выполнять необходимые локальные изменения
   и проверки. Не запрашивать повторное согласование уже выбранных решений.
4. Если меняются согласованный стек, бизнес-правила или объём работы,
   сначала обсудить это с пользователем.
5. Добавлять проверки вместе с соответствующей логикой. Проверять результат до
   объявления этапа завершённым.
6. Обновить статус этапа и текущее состояние в roadmap. Незавершённую работу
   и непроверенные критерии записать явно; не отмечать их завершёнными.
7. Сообщить, что изменено, что проверено и какие ограничения остались, затем остановиться.

Этап 0 был ограничен двумя документами: `ROADMAP.md` и `AGENTS.md`.
Git-инициализация, установка зависимостей и каркасы приложения относятся к этапу 1.
Актуальный статус этапов и выполненные проверки указаны в `ROADMAP.md`.
Если пользователь запрашивает часть этапа, не расширять запрос до всего этапа.

## Стек и структура

- Один репозиторий: `backend/` для сервера и `mobile/` для Flutter.
- Клиент: Flutter для Android/iOS, Material 3, русский язык, Riverpod без кодогенерации,
  Dio для HTTP.
- Сервер: Python 3.12, FastAPI, Pydantic 2, Uvicorn, SQLAlchemy 2, SQLite, Alembic.
- Зависимости Python управляются uv; сохранять `uv.lock` и `pubspec.lock` в Git.
- Проверки: Ruff и pytest на сервере; форматирование Dart, `flutter analyze`,
  unit- и widget-тесты на клиенте; GitHub Actions на этапе 6.
- Разделять HTTP, бизнес-логику и доступ к БД на сервере; API, состояние и виджеты
  на клиенте. Не добавлять абстракции без конкретной потребности.
- Финансовую сводку рассчитывает сервер; Flutter отображает его результат.

Не добавлять авторизацию, несколько водителей, офлайн-синхронизацию или публичный
деплой в первую версию без изменения согласованного объёма.

## Деньги и время

- Валюта KZT; сумма и комиссия — целые тенге. Не использовать `float`/`double`
  для денег ни при хранении, ни при расчётах, ни в API и клиентских моделях.
- Комиссия — денежная сумма, не процент; она неотрицательна.
- Выручка — сумма поездок; «на руки» — выручка минус комиссия.
- Разбивка `cash`/`card` относится к выручке, а не к числу поездок или чистому доходу.
- День определяется началом поездки в `Asia/Almaty`. Интервал включает полночь
  выбранного дня и исключает полночь следующего.
- Поездка через полночь целиком относится к дню начала.
- API принимает ISO 8601 с часовым смещением; время хранится и сравнивается в UTC.
  Не полагаться на системный часовой пояс или часовой пояс телефона.
- Пустой день — пустой список и нулевые показатели.

## API и повторная отправка

- Соблюдать контракт `GET /api/v1/days/{date}` и `POST /api/v1/trips` из roadmap.
- Список поездок сортировать по началу, новые сверху.
- Проверять положительную целую сумму, неотрицательную целую комиссию,
  способ оплаты `cash`/`card` и окончание строго позже начала.
- Считать ID идентификатором поездки. Одинаковый ID и нормализованные данные —
  повтор; одинаковый ID и другие данные — конфликт. Разные ID — разные поездки.
- Возвращать `201` при создании, `200` при повторе, `409` при конфликте,
  `422` при неверных данных.
- Обеспечивать уникальность ID ограничением БД и обрабатывать гонку записи.
  Проверки наличия ID перед вставкой без ограничения БД недостаточно.
- Повторный импорт JSON использует те же правила идентичности.
- Во Flutter генерировать UUID один раз на отправляемую поездку и сохранять
  ID и данные при повторе после сетевой ошибки. Блокировать двойное нажатие
  во время запроса.
- При смене даты запоздалый ответ не должен заменять данные выбранного дня.
  После добавления обновлять данные затронутого дня.

## Проверки и отчётность

- Вместе с расчётами писать тесты сумм, способов оплаты, пустого дня и границ дня.
- Вместе с API писать тесты валидации, повторов и конфликтов.
  Проверять конкурентные запросы отдельными сессиями на временной файловой SQLite.
- Проверять повторный импорт и сохранность данных после перезапуска.
- На клиенте тестировать состояние и виджеты: выбор даты, загрузку, ошибки,
  пустой день, форму, повтор отправки и обновление сводки.
- Контрольный пример: 2 поездки; выручка 3900; комиссия 585; на руки 3315;
  карта 2400; наличные 1500.
- Запускать проверки, относящиеся к изменённой части проекта. Финальный набор
  команд и мобильных сборок указан в roadmap.
- Если проверку невозможно выполнить, сообщить причину и явно обозначить её
  как непроверенную. Не выдавать наличие инструмента или успешную сборку
  за проверку пользовательского сценария.

## Репозиторий и применение ИИ

- Не сохранять в Git секреты, локальные конфигурации с секретами, рабочую SQLite-БД,
  виртуальные окружения, кеши и артефакты сборки. Демонстрационный JSON можно хранить.
- Описывать запуск и ограничения в README на этапе 6.
- По ходу работы добавлять конкретные факты в журнал использования ИИ в roadmap:
  где ИИ помог, как проверен результат, где ошибся и как ошибка исправлена.
- Не придумывать ошибки, проверки или самостоятельные исправления пользователя.
- Публикация репозитория, публичный деплой и отправка анкеты — отдельные действия
  по запросу пользователя; подготовка к сдаче их не запускает автоматически.
